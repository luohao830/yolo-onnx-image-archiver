# 公网匿名多用户推理平台重构设计

**日期：** 2026-06-09

## 1. 背景

当前仓库的真实形态是一个基于 Gradio 的单机 WebUI 推理工具。它已经具备较成熟的推理内核与结果归档能力，但整体仍偏向内部使用或单人操作场景。

当前核心代码集中在：

- `webui/app.py`：Gradio 页面入口、上传交互、任务触发
- `webui/job_manager.py`：单个后台 worker 的任务管理
- `webui/infer_worker.py`：独立推理进程
- `webui/processing.py`：图片收集、预处理、ONNXRuntime 推理、后处理、落盘、打包
- `webui/utils.py`：日志、路径与命名辅助

当前项目已经能完成以下工作：

- 上传或选择图片目录
- 上传或选择 ONNX 模型
- 批量执行 YOLO 系列 ONNX 推理
- 按检测类别归档图片
- 为未命中图片输出 `no_detection` 目录
- 按需导出 YOLO txt 标签
- 按需导出画框图片
- 按需打包输出目录为 zip

但当前项目不适合直接作为公网多人产品发布，原因包括：

- 页面层依赖 Gradio，适合工具型界面，不适合长期承载公网产品。
- 任务模型主要停留在内存和本地目录层面，没有标准化的任务状态持久化。
- 当前只有单个推理 worker，虽然页面可排队，但本质上仍是单执行通道。
- 没有管理员后台、模型发布边界、系统配置中心与任务审计能力。
- 没有面向匿名用户的任务找回机制。
- 没有为公网场景设计的上传限制、清理策略、下载授权与安全边界。

本次设计的目标是：在保留现有推理核心经验的前提下，将项目重构为一个支持公网匿名用户、多任务排队和管理员后台的单机单 GPU 推理平台。

## 2. 目标

- 将现有 Gradio 工具重构为标准 Web 产品形态。
- 面向匿名公网用户提供前台界面，无需账号即可提交任务。
- 支持两种任务模式：
  - 人员筛选模式
  - 高级模式
- 人员筛选模式固定使用管理员配置的人检模型。
- 高级模式允许用户从管理员已发布的模型中选择。
- 用户提交任务后获得 `任务编号 + 访问口令`，可稍后凭此查回任务结果。
- 引入管理员后台，使用密钥进入，可配置模型、默认策略和系统参数。
- 引入全局任务队列，支持最多 3 个任务处理器并发执行。
- 尽可能复用现有 `webui/processing.py` 中的推理和归档逻辑。
- 让系统具备明确的文件生命周期、错误状态和后续扩展空间。

## 3. 非目标

本次设计不包含以下内容：

- 不引入正式的普通用户账号体系。
- 不做多机分布式调度。
- 不做多 GPU 调度。
- 不做对象存储、消息队列或外部工作流平台接入。
- 不在首期引入复杂 RBAC 权限系统。
- 不重写现有 YOLO ONNX 推理算法细节。
- 不在首期支持任意自定义任务插件。
- 不承诺首期支持超大规模企业级高并发。

## 4. 用户已确认的边界

用户已明确确认以下决策：

- 普通用户使用匿名模式，不建立账号体系。
- 普通用户前台分为两种模式：
  - 人员筛选模式
  - 高级模式
- 人员筛选模式固定使用管理员指定的人检模型。
- 高级模式允许选择管理员发布的模型。
- 匿名用户通过 `任务编号 + 访问口令` 找回结果。
- 首期部署形态为单机单 GPU。
- 第一阶段采用前后端分离架构，后端改为标准 API 服务，而不是继续以 Gradio 为主入口。

## 5. 现状分析

### 5.1 当前项目在做什么

当前项目本质上是一个“推理归档工具”，而不是“推理服务平台”。

它的主线流程是：

1. 用户通过页面上传模型或选择现有模型
2. 用户通过页面上传图片或选择已有图片目录
3. 页面调用后台任务管理器
4. 独立 worker 进程执行推理
5. `processing.py` 批量处理图片并输出到 `images/output/<run_id>/`
6. 页面轮询 worker 事件并展示进度
7. 页面按需将输出打包成 zip 下载

### 5.2 当前项目能做什么

当前项目已经具备以下可复用能力：

- 针对 ONNXRuntime-GPU 的推理封装
- 动态读取模型类别信息
- 基于 `conf`、`iou`、类别关注列表的结果过滤
- 批量预处理、预取、后处理优化
- 将结果按类别目录组织
- 将未检出样本输出到默认未命中目录
- 输出 YOLO txt 标签
- 输出画框图片
- 将输出目录打包为 zip
- 将推理进度回传给前端

这些能力都应该在重构中尽量保留。

### 5.3 当前项目不能做什么

当前项目在平台化方向上的不足包括：

- 没有公开产品级首页和结果页
- 没有匿名用户的任务凭证机制
- 没有管理员后台
- 没有模型发布制度
- 没有持久化任务表与状态机
- 没有全局调度器与多执行槽位
- 没有文件保留与自动清理机制
- 没有面向公网的上传安全限制
- 没有统一 API 边界

### 5.4 结论

当前项目最有价值的部分是“推理内核与归档经验”，而不是“Gradio 页面本身”。

因此本次重构不应推倒重写全部逻辑，而应采用以下原则：

- 保留推理核心
- 拆掉工具型页面壳
- 重建产品化入口、任务层和管理层

## 6. 总体设计原则

### 6.1 API First

系统以标准后端 API 为中心，所有页面交互都通过 API 完成。前台用户站点和管理员后台站点均不直接调用本地 Python 函数。

### 6.2 任务中心化

上传、解压、推理、打包、下载都围绕“任务”这个实体展开。普通用户看到的是任务编号、任务进度和结果下载，而不是底层目录结构。

### 6.3 模型发布权收口到后台

普通用户不再直接上传模型。模型只能由管理员后台发布。这样可以降低误用风险，并保持系统输出可控。

### 6.4 复用成熟推理能力

现有 `webui/processing.py`、`webui/infer_worker.py`、`webui/job_manager.py` 中成熟的推理、预处理、归档与打包逻辑应尽量抽离复用，而不是完全重写。

### 6.5 渐进式迁移

系统按阶段重构，避免一次性替换所有入口带来的高风险。

## 7. 目标架构

### 7.1 架构概览

推荐目标架构如下：

- 前台用户站点
- 管理员后台站点
- FastAPI 后端服务
- 全局任务调度器
- 任务处理器池
- 本地持久化数据库
- 本地文件工作区
- 模型存储目录

### 7.2 组件职责

#### 前台用户站点

职责：

- 展示首页
- 接收图片或压缩包上传
- 让用户选择模式
- 在高级模式下展示可选模型
- 提交任务
- 展示任务编号与访问口令
- 提供任务查询页
- 提供结果下载页

#### 管理员后台站点

职责：

- 通过管理员密钥进入后台
- 上传与替换 ONNX 模型
- 上传 sidecar 类别文件
- 启用或停用模型
- 设置高级模式可见模型
- 设置默认人检模型
- 设置系统参数，如最大并发数、上传限制、保留天数
- 查看任务状态、耗时、错误日志
- 取消或重试任务

#### FastAPI 后端

职责：

- 提供用户 API
- 提供管理员 API
- 提供上传、查询、下载、配置相关接口
- 维护任务状态机
- 协调调度器与处理器池
- 进行输入校验与安全控制

#### 全局任务调度器

职责：

- 维护全局任务队列
- 控制最多 3 个任务处理器进入执行
- 控制 GPU 推理门控
- 处理任务取消、重试、超时与恢复

#### 任务处理器池

职责：

- 从任务队列中领取任务
- 解压缩上传包
- 校验图片和参数
- 调用推理内核
- 组织结果目录
- 打包结果 zip
- 更新任务状态和运行日志

#### 数据库

首期建议使用 SQLite，后续可平滑升级到 PostgreSQL。

原因：

- 当前部署目标是单机单实例
- 首期不需要引入额外数据库运维复杂度
- SQLite 足够承载任务表、模型表、配置表和日志表

### 7.3 推荐目录重组

建议将项目逐步重组为：

```text
backend/
  api/
  core/
  repositories/
  schemas/
  services/
  workers/
frontend/
  user-app/
  admin-app/
runtime/
  uploads/
  jobs/
  results/
  tmp/
models/
docs/
```

说明：

- `backend/` 负责服务、调度、数据访问与任务执行
- `frontend/user-app/` 为普通用户前台
- `frontend/admin-app/` 为管理员后台
- `runtime/` 存放运行时上传、任务工作目录、结果与临时文件
- `models/` 继续存放已发布模型与 sidecar 文件

## 8. 前台用户设计

### 8.1 首页入口

前台首页提供两个清晰入口：

- 人员筛选模式
- 高级模式

人员筛选模式应作为首页主入口，因为它最接近产品化单功能场景。

### 8.2 人员筛选模式

用户只需要：

1. 上传图片或图片压缩包
2. 点击开始处理

系统自动执行：

1. 接收文件
2. 解压压缩包
3. 扫描图片
4. 使用管理员指定的人检模型进行推理
5. 按是否检测到人输出两个目录
6. 将输出结果打包为 zip

输出 zip 内固定包含两个一级目录：

- `person/`
- `no_person/`

此模式不向用户暴露模型选择、类别过滤和推理细参数。

### 8.3 高级模式

高级模式面向熟悉模型配置的用户，保留更接近当前 Gradio 的能力，但做适度收敛。

首期允许暴露的参数包括：

- 已发布模型选择
- `conf`
- `iou`
- `batch`
- 是否导出 YOLO txt
- 是否导出画框图

高级模式不允许的能力：

- 不允许用户上传自定义模型
- 不允许访问未发布模型
- 不允许直接指定任意服务器目录

### 8.4 任务提交反馈

提交任务成功后，页面立即显示：

- 任务编号
- 访问口令
- 当前状态
- 预计处理流程说明

用户应被明确提醒保存任务编号与访问口令。

### 8.5 任务查询页

匿名用户通过以下信息找回任务：

- 任务编号
- 访问口令

查询页展示：

- 当前状态
- 排队位置或处理进度
- 成功或失败说明
- 结果下载按钮

### 8.6 上传限制

前台必须具备基础防护：

- 单任务上传文件大小限制
- 单个压缩包解压后总文件数限制
- 单个压缩包解压后总大小限制
- 仅允许图片文件和受支持压缩包格式
- 防止路径穿越和压缩包炸弹

## 9. 管理员后台设计

### 9.1 进入方式

管理员通过单独后台页面输入密钥进入。

首期采用单密钥方案即可，后续可升级为账号体系。这样可以以最小复杂度满足模型和系统配置管理需求。

### 9.2 模型管理

后台支持以下操作：

- 上传 ONNX 模型
- 上传或替换 `.names`、`.txt`、`.json` sidecar 文件
- 启用模型
- 停用模型
- 标记模型是否允许在高级模式展示
- 设置某个模型为默认人检模型

模型记录应包含：

- 模型 ID
- 显示名称
- 文件名
- 模型类型
- 是否启用
- 是否对前台可见
- 是否默认人检模型
- 创建时间
- 更新时间

### 9.3 系统配置

后台需支持配置以下参数：

- 最大任务处理器并发数，默认 3
- GPU 推理并发门控数，建议默认 1 或 2
- 上传文件大小上限
- 结果保留天数
- 临时文件清理周期
- 是否允许高级模式导出 txt
- 是否允许高级模式导出画框图

### 9.4 任务监控

后台应提供任务列表和详情页，至少展示：

- 任务编号
- 任务模式
- 模型名称
- 状态
- 创建时间
- 开始时间
- 完成时间
- 错误信息
- 结果路径

后台可执行的运维动作：

- 取消排队任务
- 取消运行中任务
- 重试失败任务
- 手动清理过期结果

## 10. 任务系统设计

### 10.1 任务状态机

推荐任务状态如下：

- `created`
- `uploaded`
- `extracting`
- `queued`
- `running`
- `packaging`
- `completed`
- `failed`
- `canceled`
- `expired`

说明：

- `created`：任务记录已生成，尚未完成上传或参数确认
- `uploaded`：上传已完成
- `extracting`：正在解压或整理上传内容
- `queued`：已进入全局等待队列
- `running`：任务处理器正在执行
- `packaging`：推理已结束，正在打包结果
- `completed`：任务成功完成，可下载
- `failed`：任务失败
- `canceled`：被用户或管理员取消
- `expired`：结果已过期，不再可下载

### 10.2 全局队列

系统维护一个全局任务队列。

默认调度策略：

- 以 FIFO 为主
- 支持管理员手动取消
- 支持管理员对特殊任务重试

此阶段不引入复杂优先级系统。

### 10.3 并发模型

用户要求最多并发 3 个任务处理器。

这里必须明确区分两个概念：

- 任务处理器并发数
- GPU 推理并发数

这两个数不应强绑定。

原因：

- 单机单 GPU 下，3 个任务同时进入 GPU 推理并不一定比串行更快
- 多模型混跑会带来显存争抢
- ONNXRuntime provider 切换和显存占用会造成波动

因此建议：

- 任务处理器并发数：默认 3
- GPU 推理并发数：配置项，默认 1，视模型与显存情况可提升到 2

这样可以允许：

- 某些任务正在解压
- 某些任务正在预处理
- 某些任务正在打包
- 只有少量任务真正进入 GPU 推理区间

### 10.4 任务处理器内部复用

每个任务处理器内部应尽量复用现有优化，包括：

- 预处理线程池
- batch 预取
- ONNXRuntime session 配置
- 后处理逻辑
- 类别归档
- 硬链接优先、复制回退
- 输出打包

### 10.5 任务取消与超时

系统需要支持：

- 取消排队任务
- 取消运行中任务
- 设置单任务最大运行时长
- 超时后自动标记失败

首期可采用轮询取消标记的方式，不要求极细粒度中断。

## 11. 推理与输出设计

### 11.1 人员筛选模式输出

人员筛选模式的结果输出必须标准化。

打包前的结果目录建议为：

```text
results/<job_id>/
  person/
  no_person/
```

最终给用户的 zip 中包含这两个目录。

### 11.2 高级模式输出

高级模式延续现有归档思路，按类别输出：

```text
results/<job_id>/
  <类别>/images/
  <类别>/labels/
```

如启用画框输出，则增加对应画框目录。

### 11.3 文件保留策略

系统需要定义清理策略：

- 上传原始文件保留较短时间
- 运行中工作目录在任务完成后按策略保留或清理
- 最终结果 zip 和结果目录保留固定天数
- 过期任务状态保留，但下载链接失效

## 13. API 边界建议

### 13.1 用户侧 API

建议包括：

- 创建任务
- 上传文件
- 查询任务状态
- 获取结果下载信息
- 列出高级模式可用模型

### 13.2 管理侧 API

建议包括：

- 管理员登录或密钥校验
- 模型上传与发布
- 系统配置读取与更新
- 任务列表查询
- 任务取消
- 任务重试

## 14. 安全与约束

### 14.1 匿名用户安全边界

需要防护：

- 非法文件类型上传
- 超大文件
- 压缩包路径穿越
- 压缩包炸弹
- 下载链接被任意猜测

因此：

- 访问口令不能明文持久化，建议存哈希
- 下载必须依赖任务编号和访问口令校验
- 文件名和解压路径必须标准化清洗

### 14.2 管理后台安全边界

首期采用管理员密钥进入后台，但仍需：

- 将密钥配置在服务端环境变量或配置文件中
- 对后台接口统一鉴权
- 记录管理员操作日志

## 15. 部署建议

### 15.1 首期部署

首期采用单机部署，包含：

- 一个 API 服务进程
- 一个调度器
- 最多 3 个任务处理器
- 一个本地 SQLite 数据库
- 一个本地模型目录
- 一个本地运行时目录

### 15.2 容器化方向

现有 Docker 结构可以继续服务于单机部署，但要逐步调整为：

- 挂载 `models/`
- 挂载 `runtime/`
- 运行 API 服务而不是 Gradio 主入口

## 16. 迁移方案

### 16.1 阶段 1：服务化推理内核

目标：

- 从 `webui/app.py` 中抽离与页面强绑定的逻辑
- 将 `processing.py`、`infer_worker.py`、`job_manager.py` 封装为可由 API 调用的服务层

完成标准：

- 不依赖 Gradio 也能通过 Python 服务接口触发推理任务

### 16.2 阶段 2：引入持久化任务模型

目标：

- 增加任务表、模型表、配置表、事件表
- 让任务状态、结果路径和错误信息落库

完成标准：

- 任务全流程信息不再只存在于内存与页面生成器中

### 16.3 阶段 3：建设新前台和管理员后台

目标：

- 上线用户前台
- 上线管理员后台
- 打通匿名任务凭证机制

完成标准：

- 用户无需进入 Gradio 页面即可提交和找回任务

### 16.4 阶段 4：灰度切换与下线旧入口

目标：

- 让新站点接管主入口
- 将旧 Gradio 页面降级为开发调试入口，或在确认无依赖后下线

完成标准：

- 线上主流量不再依赖 Gradio

## 17. 测试与验证策略

至少需要覆盖以下验证：

### 17.1 推理内核回归

- 人员筛选模式结果是否正确生成 `person/` 与 `no_person/`
- 高级模式是否正确按类别输出
- `txt` 与画框输出是否符合预期

### 17.2 任务系统验证

- 任务创建、排队、执行、失败、完成、取消、过期流程是否正确
- 匿名用户是否可凭任务编号和访问口令找回结果
- 任务并发是否遵守配置上限

### 17.3 安全验证

- 非法压缩包能否被拦截
- 路径穿越是否被阻止
- 过期任务是否无法下载
- 未持有访问口令的请求是否无法获取结果

### 17.4 管理后台验证

- 模型发布后是否可被高级模式读取
- 默认人检模型切换后，人员筛选模式是否生效
- 管理员取消或重试任务是否生效

## 18. 风险与对策

### 18.1 GPU 并发过高导致性能下降

风险：

- 单机单 GPU 下多任务同时打 GPU 可能降低吞吐甚至 OOM

对策：

- 将 GPU 推理并发独立成配置项
- 首期默认设置为 1
- 通过压测后再决定是否提高

### 18.2 文件堆积导致磁盘压力

风险：

- 匿名用户大量上传后，临时文件和结果文件可能持续堆积

对策：

- 设计过期策略
- 自动清理临时文件
- 后台提供手动清理功能

### 18.3 重构范围失控

风险：

- 同时改页面、任务、推理、部署，容易一次性改太多

对策：

- 分阶段交付
- 先服务化内核，再替换入口

## 19. 验收标准

当以下条件全部满足时，可认为本轮重构达成目标：

- 系统提供独立于 Gradio 的用户前台
- 系统提供独立管理员后台
- 普通用户可匿名提交任务
- 人员筛选模式固定输出 `person/` 与 `no_person/`
- 高级模式可选择已发布模型
- 匿名用户可凭 `任务编号 + 访问口令` 找回任务
- 系统具备全局任务队列
- 系统支持最多 3 个任务处理器并发
- GPU 推理并发与任务处理器并发可独立配置
- 管理员可配置默认人检模型与系统参数
- 现有推理和归档核心能力被复用，而非全部重写

## 20. 实现边界

实现阶段应严格围绕本设计推进，不应顺手扩展以下内容：

- 不额外引入普通用户账号体系
- 不提前做分布式调度
- 不提前接对象存储
- 不重构与当前目标无关的算法细节
- 不同时做多机多 GPU 编排

如果未来需要支持更大规模部署，应在本轮平台化重构稳定后，单独开启下一轮设计。
